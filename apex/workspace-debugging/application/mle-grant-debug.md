# MLE Grant Debugging in an APEX Workspace

Use this case when `CREATE [OR REPLACE] MLE MODULE`, `CREATE [OR REPLACE] MLE ENV`, or MLE JavaScript execution reports `ORA-01031` in an APEX-related workflow. This includes an APEX application import that fails while executing MLE DDL. An insufficient-privileges error makes a privilege issue likely; it does not identify the missing grant or prove that a particular schema lacks it.

## 1. Inspect the live failure and select the environment

- Record the exact failing operation and whether the failure occurred at module creation, environment creation, call-specification creation, or execution. If it happened during an APEX application or supporting SQL import, record that import path and the DDL step where it stopped. Note the object name, error, time, and whether the operation ran through App Builder, APEX SQL Workshop, a deployment account, or another client. Do not collect JavaScript source or secrets for this handoff.
- Establish the database release and target PDB, Workspace, application parsing schema if applicable, object owner, and actual database user/execution context. An APEX Workspace user, parsing schema, current schema, and the database user running DDL are not automatically the same identity. Mark unknown values as unknown, use available evidence first, and ask the DB owner or user only when necessary.
- For an application import, keep the APEX user who started the import, the parsing schema/object owner, and the database identity that executed the DDL as separate facts. Do not infer the DDL identity from the logged-in APEX user.
- If helpful, inspect only the existing Workspace-to-schema mapping through the permitted Workspace workflow in [schema-mapping.md](../references/workspace/schema-mapping.md). A mapping does not prove the schema has MLE privileges. Apply the main Workspace skill's identity, version, browser, and protocol rules to any live Workspace inspection.
- Inspect the user's existing APEX page first; do not rerun an installation merely to rediscover an error already visible. If the page is embedded in VS Code, use the existing VS Code window as described in [live-browser-debugging.md](../references/diagnostics/live-browser-debugging.md).
- Reuse known environment, application, connection, and protocol choices. If the environment is unknown, use the available interactive question picker (for example, `request_user_input_async` in Codex) with `Lokale Entwicklung`, `Test`, and `Produktion`; state the redacted target and read-only scope. For example: `Ist die APEX-Instanz auf <host:port> deine lokale Entwicklungsumgebung, eine Testumgebung oder Produktion?` Do not assume `localhost` means development. If a picker is unavailable, ask the same question in text.

## 2. Compare the right documentation

[APEX 26.1: About Granted Privileges](https://docs.oracle.com/en/database/oracle/apex/26.1/htmdb/about-granted-privileges.html) and its [APEX 26.2 counterpart](https://docs.oracle.com/en/database/oracle/apex/26.2/htmdb/about-granted-privileges.html) recommend a baseline list for typical database objects. They state that creating a Workspace on an existing schema does not grant database privileges to that schema; their baseline list does not include MLE grants. Neither document is an inventory of the target schema's existing or effective privileges.

For the actual MLE requirements, use the target database release's [JavaScript Developer's Guide: system and object privileges](https://docs.oracle.com/en/database/oracle/oracle-database/26/mlejs/system-and-object-privileges-required-working-javascript-mle.html). For APEX 26.2 and Oracle AI Database 26ai, Oracle's [MLE_LANGUAGES documentation](https://docs.oracle.com/en/database/oracle/apex/26.2/aeapi/APEX_INSTANCE_ADMIN.Available-Parameter-Values.html) identifies `CREATE MLE` for creating modules and environments and lists `EXECUTE ON SYS.JAVASCRIPT` for Workspace schemas. The [database release notes](https://docs.oracle.com/en/database/oracle/oracle-database/26/mlejs/changes-this-release-oracle-javascript-developers-guide.html) state that from release update 23.9 the JavaScript execute grant is no longer required for execution in one's own schema. Resolve this documentation difference against the installed release and actual operation; do not grant JavaScript execution merely because it is absent. Documentation is not proof of the incident's missing privilege.

`CREATE PROCEDURE` is relevant if the workflow creates PL/SQL call specifications. `EXECUTE DYNAMIC MLE` is relevant to dynamic execution through `DBMS_MLE`; do not infer that it is needed merely because stored modules or an MLE environment are used. For imported modules owned by another schema, ask the DB owner to check access to those specific objects. Do not propose `ANY` privileges or a broad role as the default solution.

Oracle's [Database 26 CREATE MLE MODULE reference](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/create-mle-module.html) also names `CREATE MLE MODULE`, while the MLE guide and APEX 26.2 documentation above use `CREATE MLE`. Do not assume these names are interchangeable or prescribe an additional grant based only on that wording. Verify available privilege names on the installed release through the DB skill or the fallback's read-only check.

## 3. Check privileges through SQLcl MCP

Announce the DB handoff and continue directly when the user has requested database diagnosis; do not ask again merely to switch skills. Prefer the DB skill from the active catalog or its actual local `SKILL.md` path, and follow its connection, identity, and privilege guidance. If it is absent from the catalog, check configured skill roots and actual local paths already supplied or discovered in the session; inspect the real skill before using it, and do not assume a sibling-repository path. If it cannot be found and the failure occurred while creating an MLE module or environment, use [mle-privilege-fallback.md](mle-privilege-fallback.md) for the bounded check and authorized minimal repair; do not stop solely because the DB skill is missing. For MLE execution or other database operations outside that fallback, request the DB skill or database owner. If SQLcl MCP is unavailable, explain the missing capability and stop the database portion. Use APEXlang for application import artifacts and source, but do not block the privilege check on APEXlang when the visible error already identifies the failed MLE operation.

1. Use SQLcl MCP to discover saved connections if the target is not already known. Verify the actual username, database service/PDB, and environment; never infer them from a connection label. Reuse an already-selected appropriate connection. If a connection or a switch must be selected, use the interactive question picker when available, with relevant discovered connection names and their verified username and target as needed; offer text entry for another saved name. For example: `Welche gespeicherte Datenbankverbindung soll ich für <target/PDB> verwenden?` If an administrative connection is needed, state that it will be used to apply the requested minimal grant. Do not invent connection options. A preselected option is not an answer. Respect SQLcl MCP's requirement to ask before switching an active connection; an explicit picker choice that describes the switch satisfies that request.
2. Start with read-only checks of the relevant DDL execution context and its direct, enabled-role, and object privileges. Establish the installed database release and the actual available MLE privilege names. Separate the MCP session user, the application parsing schema/object owner, and the historic DDL execution identity. SQLcl MCP may audit its SQL statements; do not copy credentials, session IDs, SQL bodies, or unrelated data into the protocol.
3. If historical DDL identity is unavailable, use reliable installed-application metadata and the user's confirmation when needed to establish which schema needs the privilege. Do not claim that the MCP user, a same-named workspace, or ownership of another object proves the historical DDL identity. If the grantee, PDB, or missing right cannot be established, stop before changing grants and ask only for the missing fact.

## 4. Apply an authorized minimal repair and verify it

- **Diagnosis only:** If the user says read-only, no grants, or wait for a separate go-ahead, report the evidence and smallest conditional grant proposal; do not execute it or retry the script.
- **Diagnosis and repair:** If the user has explicitly requested a fix or authorized the needed grants, select the missing privilege and exact grantee only after verifying the target and operation. If an administrative connection is needed, ask once with the connection picker, including an available `SYSTEM` connection when appropriate. Explain that it will be used for the targeted privilege repair; when already known, include the exact privilege, grantee, and PDB in that same question. A selected connection authorizes the connection switch, while the user's explicit repair instruction authorizes the verified minimal fix. Do not ask for a second generic approval merely for the handoff or repeat a previously answered choice. Follow any tool-level action-time confirmation requirement.
- If the user has not yet authorized a grant and has not prohibited one, present the exact privilege, grantee, PDB, and effect in one structured question and wait for an explicit choice. When an administrative connection must also be chosen and the grant is already known, combine both into that same picker: offer the discovered connection with a label that explicitly authorizes the stated grant, alongside a read-only option. A choice explicitly accepting both authorizes both the switch and that grant; do not ask a duplicate question. Never treat a default or an unanswered question as approval. Preserve an explicit prohibition until the user changes it.
- Through the DB skill and selected SQLcl MCP connection, or the narrow fallback when the DB skill is unavailable, execute only the confirmed minimal grant, then verify it with a fresh read-only privilege check. Do not grant `ANY` privileges, a broad role, or additional JavaScript/dynamic-MLE rights by default.
- For a confirmed missing own-schema `CREATE MLE` privilege, the narrow candidate is `GRANT CREATE MLE TO <verified_schema>;`. Substitute only the verified grantee on the verified PDB; this example does not authorize the action or establish the grantee.
- Retry only when the user authorized running the affected script or creating the missing objects. Inspect the live installation flow first: isolate the failed MLE script and preserve existing tables and data. If the installer would also run unreviewed or destructive scripts, stop and present that exact action rather than rerunning everything. Prefer the APEXlang/DB owner for script execution; the fallback may use the existing APEX UI for the bounded retry without editing or reconstructing source. Verify resulting object status and errors.

Report the visible failed step, verified identities and grants, the action actually taken, post-check results, and remaining uncertainty. A privilege fix or valid object is not proof that the JavaScript, application, or external integration works.
